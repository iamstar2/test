## 0. 시작하기 전에 — 강의 자료 정독 결과 3가지

### 0-1. "이 교시의 산출물" 블록은 1·2·3교시에만 명시되어 있습니다

HTML을 파싱해 확인한 결과 `이 교시의 산출물` 카드는 **정확히 3개**(1교시, 2교시, 3교시)만 존재합니다. 4·5·6교시에는 해당 블록이 없습니다.

이것은 누락이 아니라 강의 구조상 의도로 보입니다. 4·5·6교시의 산출물은 **Final 챕터의 「하드웨어 시스템 설계서」로 직접 흡수**되기 때문입니다. Final 챕터가 보유한 구성 요소는 다음과 같습니다.

- 블록 다이어그램 (전원 배선 뷰 / 신호 배선 뷰 2종)
- 핀 연결표 · ESP32-S3
- 예상 비용 · 1대 기준
- 테스트 계획 T1~T6
- 예상 문제와 대책 6종

**따라서 본 보고서는 1~3교시는 명시된 산출물 목록을 그대로 따르고, 4~6교시는 각 교시의 인터랙티브(Interactive 09~16)가 요구하는 결정 사항과 Final 설계서 항목을 역산해 산출물을 정의**했습니다. 해당 부분은 `※ 도출 산출물`로 표기했습니다.

### 0-2. VIRA-1은 강의의 5계층 프레임에 그대로 들어갑니다

강의는 Physical AI를 5계층으로 정의하고 "하나라도 빠지면 제품은 죽는다"고 규정합니다. VIRA-1은 이동 로봇이 아니지만 **감지 → 판단 → 행동**의 물리 루프를 갖는 Physical AI 시스템이므로 매핑이 성립합니다.

### 이 표에서 읽어야 할 단 하나의 숫자 — **피크 / 평균 = 2.23배**

강의가 Interactive 02에서 강조하는 지점이 정확히 여기입니다. 특히 조명 계통(24V-ILL)만 떼어 보면:

```
평균 16.8 W  →  피크 156.0 W   ( 9.3배 )
```

**조명은 평균으로 보면 있으나 마나 한 부하지만, 피크로 보면 시스템에서 두 번째로 큰 부하입니다.** 스트로브는 200µs 동안만 발광하므로 평균 전류는 작지만, 그 200µs 동안에는 6.2A를 요구합니다. 평균값 기준으로 SMPS를 고르면 **발광할 때마다 24V 레일이 내려앉고, 같은 레일에 물린 스텝모터 드라이버가 오동작**합니다.

이것이 강의 Interactive 03(모터를 켜면 보드가 재부팅되는가)이 말하는 브라운아웃과 완전히 같은 메커니즘입니다.

### 왜 24V를 조명(ILL)과 구동(ACT)으로 쪼갰는가 — 이 설계의 핵심 결정

강의는 `RAILS`에서 5V를 **5V-A(Pi용 5A)** 와 **5V-B(ESP32·센서·서보용 2A)** 로 나눕니다. 이유는 "Raspberry Pi 5는 피크에서 3A까지 먹는다"와 "서보 스톨 전류까지 합쳐 피크 1.3A"가 **서로를 흔들지 않게** 하기 위함입니다.

VIRA-1에서 같은 논리가 적용되는 쌍은 **스트로브 조명 ↔ 스텝모터**입니다.

- 스트로브는 200µs 단위의 **극단적으로 짧고 큰** 전류를 요구합니다
- 스텝모터 드라이버는 수십 ms 단위의 **길고 중간 크기** 전류를 요구합니다
- 두 부하를 한 레일에 묶으면, **스트로브 발광 순간의 전압 강하가 스텝모터의 전류 제어 루프에 실시간 외란으로 들어갑니다**
- 그 결과는 스테이지 위치 오차 → 이미지 흔들림 → **AI 인식률 하락**입니다

즉 이것은 전원 문제가 아니라 결국 **검출 성능 문제로 되돌아옵니다.** 강의 5교시가 말하는 "기구가 곧 성능이다"의 전원 버전입니다.

### 여유율보다 중요한 것 — 스트로브 벌크 커패시터

강의의 「예상 문제와 대책」은 재부팅 대책으로 `전원 라인 분리 · 커패시터 · 가속 램프업` 3종을 제시합니다. VIRA-1에서 **커패시터**가 가장 결정적입니다.

```
필요 용량 C = I_peak × t_flash / ΔV_허용
            = 6.2 A × 200 µs / 0.5 V
            = 2,480 µF
```

**→ 스트로브 컨트롤러 입력단에 3,300 µF 저ESR 전해 커패시터 뱅크 배치** (2,480 µF에 마진 33%)

핵심은 **커패시터를 SMPS 옆이 아니라 LED 드라이버 바로 앞에 두는 것**입니다. 배선 인덕턴스가 피크 전류의 상승 구간을 방해하므로, 커패시터가 부하에서 멀면 용량이 아무리 커도 소용이 없습니다. 6.2A를 SMPS가 아니라 커패시터가 공급하게 만드는 것이 목적입니다.

> **강의의 "가속 램프업" 대응 항목** — VIRA-1에서는 스트로브에 램프업을 쓸 수 없습니다(발광 파형이 곧 노출이므로). 대신 **스텝모터 3축의 기동 시퀀스를 시간축에서 분리**하는 것으로 대체합니다. Z축 하강 → 진공 척 ON → 셔틀 이동을 겹치지 않게 배치하면 24V-ACT의 실제 피크는 4.4A가 아니라 약 2.7A로 내려갑니다.

## 산출물 ③ — 전원 블록도

강의는 `12V / 5V-A / 5V-B`의 3계통 분리를 요구합니다. VIRA-1은 **5계통**입니다.

```
                    AC 220V (팹 계통)
                          │
                  ┌───────┴───────┐
                  │  UPS (5kVA)   │  ← IPC·모션 컨트롤러만 백업. 조명·구동은 미백업
                  └───────┬───────┘
                          │
    ┌────────┬────────────┼────────────┬────────────┐
    │        │            │            │            │
┌───▼────┐ ┌─▼────────┐ ┌─▼────────┐ ┌─▼────────┐ ┌─▼──────────┐
│ATX 600W│ │SMPS 24V  │ │SMPS 24V  │ │SMPS 5V   │ │PoE+ 스위치 │
│        │ │  /10A    │ │  /6A     │ │  /4A     │ │   60W      │
│PSU-ATX │ │ 24V-ILL  │ │ 24V-ACT  │ │5V-LOGIC  │ │   PoE      │
└───┬────┘ └─┬────────┘ └─┬────────┘ └─┬────────┘ └─┬──────────┘
    │        │  ┌─────┐   │            │            │
    │        ├──┤3300µF│  │            │            │
    │        │  └─────┘   │            │            │
 IPC+GPU   스트로브 3ch  Z축·셔틀·   모션 컨트롤러  카메라 ×3
  ×2       (다크필드2   진공밸브·팬   엔코더·센서

```

**UPS 백업 범위를 IPC·모션 컨트롤러로 한정한 근거** — 정전 시 필요한 것은 "계속 검사하는 것"이 아니라 **"지금까지의 판정 결과와 웨이퍼 맵을 안전하게 저장하고, 픽업 헤드를 안전 위치로 복귀시키는 것"** 입니다. 조명과 구동부까지 백업하려면 UPS 용량이 3배가 되는데, 그 돈으로 얻는 것은 정전 중 몇 분의 추가 검사뿐입니다. 반면 판정 데이터 유실은 로트 전체의 재검사를 유발합니다. (선행 문서 KPI: 검사 데이터 유실률 ≤ 0.01%)

```
   │ 신호 GND  │   │파워 GND│ │섀시 GND│ │ESD 접지│ │프레임 접지│
   │(로직·센서)│   │(조명·  │ │(인클로 │ │(작업면 │ │(스테이지 │
   │           │   │ 구동)  │ │ 저·PC) │ │ ·손목대)│ │  ·척)    │
   └───────────┘   └────────┘ └────────┘ └────────┘ └──────────┘
```

**설계 규칙 4가지**

1. **신호 GND와 파워 GND는 배선상 분리하고, 접지 버스바 한 점에서만 만난다.** 스트로브 6.2A의 리턴 전류가 센서 신호 GND를 타고 흐르면, 그 전압 강하가 그대로 아날로그 센서 값의 오차가 됩니다.
2. **카메라 섀시 접지는 한 쪽에서만 잡는다.** 카메라와 IPC 양쪽에서 접지하면 그라운드 루프가 생기고, 루프에 유도된 전류가 GigE 신호에 커먼모드 노이즈로 실려 **이미지에 주기적 가로줄**로 나타납니다. 이 노이즈는 회로 패턴과 구분되지 않아 선형 결함 오검을 유발합니다.
3. **ESD 접지는 1MΩ 직렬 저항을 경유한다.** (ANSI/ESD S20.20) 직결하면 정전기가 빠지는 게 아니라 인체가 감전 경로가 됩니다.
4. **접지 저항 실측 ≤ 4Ω, 각 지점 간 전위차 ≤ 1V.** 설치 검증 항목(§Final T1)에 포함합니다.

> ⚠️ **강의 문장 그대로 적용** — "5V 신호를 3.3V 핀에 그대로 넣으면 핀이 손상될 수 있다. 분압 저항이나 레벨 시프터가 필요하다."
> VIRA-1 대응: **24V 산업 표준 DI/DO와 5V 로직 간에는 반드시 포토커플러 절연을 둡니다.** 팹 I/O는 24V가 기본이며, 스트로브·솔레노이드의 유도성 부하 차단 시 발생하는 역기전력이 로직단으로 들어오면 컨트롤러가 파괴됩니다. 플라이백 다이오드도 각 유도성 부하에 개별 배치합니다.

## 산출물 ① — 컴퓨팅 역할 분담표

강의 Interactive 04는 MCU와 SBC를 5개 축으로 비교합니다. 그중 VIRA-1 설계를 결정한 두 축을 그대로 인용합니다.

| 비교 축 | MCU (ESP32-S3) | SBC (Raspberry Pi 5) | VIRA-1 시사점 |
|---|---|---|---|
| **부팅 시간** | 0.3초 | 35초 | **IPC 부팅 중 소터는 안전 정지 상태여야 한다** |
| **실시간 제어 정밀도** | 매우 높음 — "OS 간섭이 없어 마이크로초 단위 타이밍이 일정하다" | 낮음 — "OS 스케줄러 때문에 가끔 수십 ms씩 밀린다" | **촬상 트리거를 IPC가 내면 안 된다** |

VIRA-1의 대응 관계는 `MCU → 모션 컨트롤러`, `SBC → 산업용 IPC + GPU` 입니다.

### 역할 분담표

강의 `ROLES` 배열과 동일한 형식(기능 / 배치 / 근거)으로 작성했습니다.

| # | 기능 | 배치 | 배치 근거 |

| 6 | **배출 실패 인터록 · 라인 정지** | **모션 컨트롤러** | 동일. IPC가 죽어도 인터록은 살아 있어야 한다 |

| 8 | 마스크 → µm 환산, 스펙 대조, 3분기 판정 | **IPC** | 룰 기반 후처리. 실시간성 요구가 낮고 파라미터 변경이 잦다 |

| 12 | 환경센서 폴링 (온습도·진동·조도·파티클) | **모션 컨트롤러** | 강의: "저전력으로 계속 켜둘 수 있어야 한다". IPC 재부팅 중에도 환경 감시는 끊기면 안 된다 |

### 이 분담표에서 도출되는 안전 요구사항 2가지 ★

강의의 부팅 시간 축(0.3초 vs 35초)을 VIRA-1에 대입하면 **설계 요구사항이 두 개 튀어나옵니다.** 이것은 강의 자료에는 없지만 논리적 귀결입니다.

**요구사항 A — IPC 부팅 중 소터 안전 상태 유지**
IPC 부팅에 약 40초가 걸립니다. 그동안 모션 컨트롤러는 이미 살아 있습니다. 만약 컨트롤러가 "판정 없음 = 통과"로 동작하면, **부팅 40초 동안의 다이 약 160개가 무검사로 흘러갑니다.**
→ **기본 상태(default state)를 `HOLD`로 설계합니다.** IPC로부터 유효한 heartbeat를 받기 전까지 픽업을 시작하지 않습니다.

**요구사항 B — IPC 다운 시 stale verdict 차단**
IPC가 로트 중간에 죽으면, 컨트롤러의 큐에는 아직 소비되지 않은 판정이 남아 있습니다. 이걸 그대로 쓰면 **다른 다이의 판정으로 픽업**하게 됩니다.
→ 판정 패킷에 **다이 좌표(Row, Col) + 시퀀스 번호 + 타임스탬프**를 실어, 컨트롤러가 현재 픽업 대상과 대조합니다. 불일치 시 즉시 인터록.

> 이 두 요구사항은 강의 5계층 중 **컴퓨팅 계층이 죽었을 때의 실패 모드**("판단하는 주체가 없다. 센서 값은 들어와도 아무 결정이 내려지지 않는다")를 VIRA-1 문맥에서 구체화한 것입니다.

### VIRA-1의 "ADC2 함정"은 무엇인가 — 네트워크 대역폭 충돌

강의의 ADC2 규칙이 가르치는 것은 **"어떤 자원은 다른 기능을 켜는 순간 쓸 수 없게 된다"** 는 구조입니다. VIRA-1에서 이 구조가 그대로 재현되는 지점은 **카메라 3대의 GigE 대역폭**입니다.

```
프레임 크기   2448 × 2048 × 1 byte (mono 8bit) = 5.01 MB
3채널 동시    15.04 MB / 프레임
웨이퍼당      578 프레임 (§4에서 산출)
스캔 시간     89.6 초
────────────────────────────────────────────
필요 대역폭   97 MB/s = 776 Mbps
```

| 배선 방식 | 채널당 대역폭 | 1GbE 실효(940Mbps) 대비 여유 | 판정 |
|---|---|---|---|
| 카메라 3대 → 스위치 → **NIC 1포트** | 776 Mbps | **+21%** | ❌ **위험** |
| 카메라 3대 → **독립 NIC 3포트** | 259 Mbps | **+263%** | ✅ 안전 |

**단일 포트 여유 21%는 설계 여유가 아닙니다.** 점보 프레임 설정 누락, 재전송, PoE 부하 변동만으로도 즉시 프레임 드롭이 발생합니다. 그리고 프레임 드롭은 **해당 다이의 무검사 통과**를 의미합니다.

> **강의의 교훈이 그대로 적용됩니다.** "핀은 빈 자리가 아니라 정해진 자리다" → **"NIC 포트는 빈 자리가 아니라 대역폭이 정해진 자리다."**

|---|---|---|
| **I2C** | "2가닥 + 주소. 여러 센서를 한 버스에. → 센서가 많을 때 1순위" | ✅ **환경센서 4종 전부** — 저속·소량·다수. 정확히 I2C의 영역 |
| **SPI** | "4가닥 + CS. 수 MHz로 빠르다. → 디스플레이, SD카드" | ❌ 해당 부하 없음 |
| **UART** | "2가닥 · 1:1. 한 명과만 대화" | ✅ 파티클 카운터 1대 |

## 산출물 ② — I2C 주소 정리된 핀맵 v1

강의 Interactive 08의 경고: **"같은 주소를 가진 센서가 둘이면 버스는 무너진다."**
강의 `I2CLIB`가 제시한 주소 변경 방법을 그대로 적용했습니다.

| 디바이스 | 위치 | 기본 주소 | **확정 주소** | 변경 방법 | 근거 |
|---|---|---|---|---|---|
| 진동 센서 #1 (IMU) | 카메라 마운트 | 0x68 | **0x68** | 기본값 유지 | — |
| 진동 센서 #2 (IMU) | 스테이지 베이스 | 0x68 | **0x69** | **AD0 핀 HIGH** | 강의 `I2CLIB` 명시 방법 |
| 온습도 #1 (BME280) | 제어반 내부 | 0x76 | **0x76** | 기본값 유지 | — |
| 온습도 #2 (BME280) | 인클로저 내부 | 0x76 | **0x77** | **SDO 핀 설정** | 강의 `I2CLIB` 명시 방법 |
| 조도 센서 (BH1750) | 인클로저 상단 | 0x23 | **0x23** | 기본값 유지 | 1개뿐이라 충돌 없음 |

**버스 구성**

```
모션 컨트롤러 (I2C Master, 3.3V)
   │  SDA ─┬──────┬──────┬──────┬──────┐
   │  SCL ─┴──────┴──────┴──────┴──────┘
   │        0x68   0x69   0x76   0x77   0x23
   │       진동1  진동2  온습1  온습2   조도
   └── 풀업 저항 4.7kΩ ×2 (버스에 단 1쌍만)
```

**설계 유의점 3가지**

1. **풀업 저항은 버스 전체에 1쌍만.** 센서 모듈마다 내장 풀업이 있으면 병렬로 합성되어 저항이 낮아지고, 신호 엣지가 무너집니다. 모듈의 풀업 저항을 제거하거나 점퍼로 분리해야 합니다.
2. **총 배선 길이 1m 이내, 100kHz 표준 모드.** I2C는 원래 보드 내 통신용입니다. 인클로저 곳곳에 흩어진 센서를 긴 배선으로 묶으면 정전용량이 커져 통신이 실패합니다. 1m를 넘으면 I2C 버스 익스텐더 또는 개별 UART/디지털 센서로 교체합니다.
3. **강의가 경고한 `VL53L0X`(0x29) 유형에 주의.** 주소 변경 핀이 없는 부품은 *"두 번째 I2C 버스 또는 멀티플렉서 필요"* 합니다. 현재 선정 목록에는 해당 부품이 없지만, **향후 센서 추가 시 주소 변경 가능 여부를 선정 기준에 반드시 포함**합니다.

> **부팅 시 I2C 스캔 결과를 로그로 출력하도록 설계합니다.** 강의 6교시의 진단 케이스 *"I2C 센서 2개 중 1개만 읽힌다 → 주소 충돌이다. I2C 스캔을 돌리면 즉시 보인다"* 에 대한 선제 대응입니다.

## 산출물 ① — 광학 분해능 확정

강의의 명제: **"해상도는 높일수록 좋은 것이 아니다."**
Interactive 09는 해상도를 올릴 때 `추론 지연 · 프레임 데이터량 · 소비 전력 · 모듈 비용` 4가지가 함께 나빠짐을 보여주고, **"잎의 병징(작은 반점)을 식별해야 합니다"** 라는 기준으로 최소 해상도를 고르게 합니다.

VIRA-1의 "잎의 병징"에 해당하는 것은 **최소 검출 대상 결함 폭 15 µm**입니다.

### 분해능 5.0 µm/px 확정 근거

```
최소 검출 결함 폭   15 µm
분해능              5.0 µm/px
────────────────────────────
마스크 폭            3 px   ← 학습 리포트의 mask_ratio 논의가 성립하는 하한
```

| 분해능 | 15µm 결함의 픽셀 폭 | FOV | 웨이퍼당 프레임 | 판정 |
|---|---|---|---|---|
| 10.0 µm/px | **1.5 px** | 24.5 × 20.5 mm | 145 | ❌ **광학 단계에서 이미 소실.** 모델로 복구 불가 |
| **5.0 µm/px** | **3 px** | 12.24 × 10.24 mm | **578** | ✅ **채택** |
| 2.5 µm/px | 6 px | 6.12 × 5.12 mm | **2,312** | ❌ 프레임 4배 → 스캔 시간·데이터·추론 모두 4배 |

**왜 더 올리지 않는가** — 2.5 µm/px로 가면 검출 성능은 다소 올라가겠지만, 프레임 수가 578 → 2,312로 **4배**가 됩니다. 스캔 시간 90초 → 360초, 일 데이터량 467 GB → 1.87 TB, 추론 부하 4배입니다. 강의가 Interactive 09에서 정확히 경고하는 상황입니다.

**왜 더 내리지 않는가** — 10 µm/px에서 15µm 크랙은 1.5 px입니다. 학습 리포트가 지적한 `mask_ratio=4`로 인한 소실 문제(5px → 1.25px)와 **똑같은 손실이 광학 단계에서 먼저 일어납니다.** 그리고 광학에서 잃은 정보는 어떤 하이퍼파라미터로도 복구되지 않습니다.

> **이 결정이 학습 설계와 한 줄로 연결됩니다.**
> `광학 5.0 µm/px` → `다이 4.0×3.1mm = 800×620 px` → `학습 리포트 실측 이미지 811×624 px과 정합` → `imgsz=832 상한` → `타일링 불필요`
> 학습 리포트의 *"해상도 상한은 VRAM이 아니라 데이터가 정합니다"* 는 한 단계 더 거슬러 올라가면 **"데이터의 상한은 광학이 정합니다"** 가 됩니다.

### 스캔 아키텍처 — 프레임당 9 다이

5MP 센서(2448×2048)로 FOV 12.24 × 10.24 mm를 확보하면 다이 **3 × 3 = 9개**가 한 프레임에 들어옵니다.

| 항목 | 값 | 산출 |
|---|---|---|
| 웨이퍼당 프레임 | **578** | net die 5,200 ÷ 9 |
| 프레임당 데이터 (3ch) | 15.04 MB | 2448×2048×1B × 3 |
| 웨이퍼당 원본 데이터 | 8.49 GB | 578 × 15.04 MB |
| **일 데이터량 (55매)** | **467 GB/일** | — |

> ⚠️ **선행 문서 정정** — `spec_v2` §6-4에 기재한 *"일 283,000 다이 × 3채널 ≈ 일 1.2 TB"* 는 **과대 추정**이었습니다. 다이 단위가 아니라 프레임 단위로 저장하면 실제는 **약 467 GB/일**입니다. 스토리지 40TB 기준 보존 가능 기간이 약 33일 → **약 85일**로 늘어납니다. 보존 정책 재검토를 권고합니다.

### 스캔 타이밍 — 검사는 병목이 아니다 ★

| 항목 | 값 | 산출 |
|---|---|---|
| 픽업 기준 웨이퍼 1매 소요 | 1,300 초 (21.7분) | 5,200 다이 × 250 ms |
| **스캔 허용** 스텝 시간 | 2,249 ms | 1,300 s ÷ 578 프레임 |
| **실제** 스텝 시간 | **155 ms** | 이송 60ms + 정정 80ms + 촬상 15ms |
| 웨이퍼 스캔 소요 | **89.6 초 (1.5분)** | 578 × 155 ms |
| **여유율** | **14.5 배** | 1,300 ÷ 89.6 |

**결론: 광학 스캔은 택트를 전혀 잡아먹지 않습니다.** 병목은 픽업입니다.

이로부터 **스캔–추론–픽업 3단 비동기 파이프라인**이 도출됩니다.

```
웨이퍼 N   [스캔 90s] → [추론 ~600s] → [픽업 1300s]
웨이퍼 N+1              [스캔 90s]  → [추론 ~600s] → [픽업 1300s]
                                       ↑
              픽업이 시작될 때 판정은 이미 전부 나와 있다
```

- 다이당 추론 실효 예산 = 1,300 s ÷ 5,200 = **250 ms/다이** → KPI(P95 120ms) 대비 **여유 2.1배**
- 프레임 9다이를 직렬 추론하면 9 × 120 = 1,080 ms > 스텝 155 ms → **스캔과 추론을 같은 스레드에 묶으면 즉시 병목.** 반드시 큐로 분리하고 GPU는 배치 추론

강의 `PROTOS`는 4개 후보를 `최대 거리 / 최대 데이터량 / 전력`으로 비교합니다. 그중 VIRA-1 판정에 결정적인 항목:

## 산출물 ① — 드라이버 경유 구조

강의 Interactive 12는 `GPIO 최대 40mA` vs `모터 기동 1200mA` = **30배 초과**를 보여줍니다. VIRA-1의 대응 수치는 더 극단적입니다.

| 항목 | 값 |
|---|---|
| 모션 컨트롤러 DO 정격 | 100 mA |
| **스트로브 피크 전류 (3ch 동시)** | **6,200 mA** |
| **초과 배율** | **62 배** |

**→ DO 직결은 컨트롤러 출력단 즉시 파괴.** 강의 원칙 3 *"MCU는 지시만, 힘은 드라이버가 쓴다"* 가 그대로 적용됩니다.

```
  ❌ 금지                          ✅ 채택
  ┌──────────┐                    ┌──────────┐
  │ 컨트롤러  │                    │ 컨트롤러  │
  │   DO     │                    │   DO     │  5V TTL, 수 mA
  └────┬─────┘                    └────┬─────┘
       │ 6.2 A ✗                       │ 지령만
  ┌────▼─────┐                    ┌────▼─────────────┐
  │ LED 어레이│                    │ 정전류 드라이버   │◄── 24V-ILL
  └──────────┘                    │ + 3300µF 뱅크    │    (6.2A는 여기서)
                                   └────┬─────────────┘
                                   ┌────▼─────┐
                                   │ LED 어레이│
                                   └──────────┘
```

**정전류(constant current) 드라이버여야 하는 이유** — 정전압 구동은 LED 온도가 오르면 전류가 늘어나 광량이 변합니다. **광량 변동은 곧 이미지 밝기 변동이고, 다크필드에서 밝기 변동은 결함 스코어를 직접 흔듭니다.** 4시간 연속 가동 후 미검율이 올라가는 전형적 원인이며, 강의 6교시의 진단 케이스 *"시간이 지날수록 나빠진다 → HW · 발열"* 에 해당합니다.

## 산출물 ② — 액추에이터 선정표

강의 `ACT`의 결정 트리를 그대로 적용했습니다.

> 질문 1: 계속 회전해야 하는가? → **DC / 기어드 DC 모터**
> 질문 2: 정해진 각도로 움직이는가? → **서보 모터**
> 아니면 → **릴레이 / MOSFET** (*"켜고 끄기만 한다. 큰 전원을 작은 신호로 스위칭한다"*)

| 부하 | 결정 트리 경로 | 선정 | 드라이버 | 근거 |
|---|---|---|---|---|
| **스트로브 LED ×3** | 계속 회전 ✗ / 각도 ✗ → 켜고 끄기 | **MOSFET 정전류 드라이버** | 전용 스트로브 컨트롤러 | **릴레이 불가.** 릴레이 응답은 ms 단위인데 필요 정밀도는 200µs. 기계식 접점으로는 원리적으로 불가능 |
| **픽업 Z축** | 계속 회전 ✗ / **각도(위치) ✓** | **스텝모터 + 리니어 가이드** | 마이크로스텝 드라이버 | 위치 반복정밀도가 픽업 성공률을 결정 |
| **3-Bin 셔틀** | 계속 회전 ✗ / **위치 ✓** | **스텝모터** | 마이크로스텝 드라이버 | 3위치 인덱싱 |
| **진공척** | 계속 회전 ✗ / 각도 ✗ → 켜고 끄기 | **솔레노이드 밸브** | 릴레이 + **플라이백 다이오드** | 강의: *"펌프·조명·220V 기기에 쓴다"* 와 동일 유형. 유도성 부하이므로 역기전력 대책 필수 |
| **인클로저 팬** | **계속 회전 ✓** | **DC 팬** | PWM | 강의: *"바퀴·팬에 쓴다"* |

> **강의의 토크 계산(Interactive 13)은 VIRA-1에 직접 적용되지 않습니다.** `need = (무게 × 바퀴반경 × 노면계수) / 바퀴수 × 1.5` 산식은 이동 로봇 전용입니다.
> VIRA-1의 등가 항목은 **스테이지 이송·정정 시간 예산**이며, §산출물 ③에서 다룹니다. 강의가 토크에 1.5배 마진을 두는 것과 같은 취지로, 정정 시간에도 마진을 둡니다.

## 산출물 ③ — 기구 요구사항 · 진동 예산 ★

강의는 「무게중심 / 진동」 카드에서 이렇게 못 박습니다.

> **"모터 진동 → 카메라 흔들림 → AI 인식률 하락. 기구가 곧 성능이다."**

그리고 6교시 진단 케이스에서 다시 한번:

> *"Pi에서 테스트할 땐 잘 맞는데 로봇에 올리면 인식률이 떨어진다"* → *"모델이 아니라 입력이 달라진 것이다. **주행 진동으로 인한 블러**, 조명 변화, RGB/BGR 반전을 먼저 의심한다."*

**VIRA-1에서 이 명제는 정량화됩니다.** 분해능이 5.0 µm/px이므로, **잔류 진동 5 µm = 이미지 1 px 블러**입니다.

### 정지 촬상 vs 이동 촬상 판정

| 스테이지 속도 | 발광 시간 | 이동량 | 픽셀 환산 | 판정 |
|---|---|---|---|---|
| 200 mm/s | 200 µs | 40.0 µm | **8.00 px** | ❌ |
| 200 mm/s | 50 µs | 10.0 µm | **2.00 px** | ❌ |
| 100 mm/s | 50 µs | 5.0 µm | **1.00 px** | ❌ 경계 |
| 50 mm/s | 50 µs | 2.5 µm | 0.50 px | ⚠️ 광량 부족 우려 |
| **정지 (Step & Settle)** | 200 µs | ~0 µm | **0 px** | ✅ **채택** |

**→ Step & Settle 방식 확정.** 이동 중 촬상(on-the-fly)은 발광 시간을 50µs 이하로 줄여야 하는데, 그러면 다크필드 산란광의 광량이 부족해집니다. §4에서 확인했듯 **스캔 여유가 14.5배**이므로 정지 촬상의 시간 손실을 충분히 감당할 수 있습니다. 속도를 살 이유가 없습니다.

### 진동 예산 배분

| 항목 | 허용값 | 근거 |
|---|---|---|
| 스테이지 정정 시간 (settling) | **80 ms** | 정정 완료 판정 = 잔류 진동 진폭 < 2 µm (0.4 px) |
| 촬상 시점 잔류 진동 | **< 2 µm (0.4 px)** | 1 px 미만에 마진 2.5배 |
| 인클로저 외부 진동 전달 | **< 1 µm** | 제진 마운트 4점 지지 |
| 팬 진동 | **< 0.5 µm** | 카메라 마운트와 팬을 같은 프레임에 두지 않음 |

**설계 규칙**
1. **카메라 마운트와 스테이지 구동부를 기계적으로 분리한 프레임에 배치.** 강의의 *"배터리는 낮고 가운데로"* 와 같은 취지 — 진동원과 민감부를 떼어놓습니다.
2. **진동 센서 2개(0x68 / 0x69)로 상시 감시.** 카메라 마운트 값이 임계를 넘으면 해당 프레임을 재촬상하고, 지속되면 알람.
3. **정정 완료를 시간이 아니라 실측으로 판정하는 옵션을 남겨둡니다.** 80ms 고정은 초기값이며, 진동 센서 실측 기반 적응형 대기가 더 안전합니다.

## 산출물 ① — 진단 순서

강의 `STEPS`는 10단계 진단 순서를 정의합니다: `1 전원 → 2 공통 GND → 3 배선 → 4 전압 → 5 GPIO 번호 → 6 장치 인식 → 7 통신 → 8 센서 데이터 → 9 AI 모델 → 10 액추에이터`

핵심은 **"디버깅은 감이 아니라 순서다"** 이며, 마지막 문장이 이 교시의 결론입니다.

> **"AI가 짜준 코드를 고치기 전에, 전원과 GND부터 확인한다."**

VIRA-1 버전으로 재정의했습니다.

| 단계 | 항목 | 확인 방법 | 통과 기준 |
|---|---|---|---|
| **1** | 전원 | 각 레일 무부하 실측 | ATX 12V / 24V-ILL / 24V-ACT / 5V, 오차 ±5% 이내 |
| **2** | 접지 | 접지 저항 · 지점 간 전위차 | ≤ 4Ω / ≤ 1V |
| **3** | 배선 | 절연 DI/DO 도통, 엔코더 A/B/Z 차동 | 전 채널 도통, 극성 정상 |
| **4** | 부하 시 전압 | **스트로브 발광 중 24V-ILL 실측 (오실로스코프)** | 강하 ≤ 0.5V |
| **5** | 채널 할당 | 트리거·스트로브 채널 번호 대조 | 설계표와 100% 일치 |
| **6** | 장치 인식 | **I2C 스캔 · GigE 카메라 열거 · GPU 인식** | 5개 I2C 주소 + 카메라 3대 + GPU 2매 전원 인식 |
| **7** | 통신 | EtherCAT 사이클, SECS/GEM 핸드셰이크, MQTT 연결 | 유실 0, 재연결 성공 |
| **8** | 입력 데이터 | 촬상 이미지 육안 확인 · 환경센서 값 | 블러 없음, 광량 정상, 센서 값 물리적 타당 |
| **9** | AI 모델 | 알려진 불량 다이 시험편 투입 | Critical 검출률 ≥ 99.5% |
| **10** | 액추에이터 | 3-Bin 분류 · 인터록 동작 | 오분류 0건, 인터록 100% 작동 |

> **6단계(장치 인식)를 통과하기 전에 9단계(AI 모델)를 의심하지 않습니다.** 강의 진단 케이스 *"코드는 올라가는데 모든 센서 값이 0이다"* 의 해설: *"먼저 6단계(장치 인식)로 살아있는지 보고, 죽어 있으면 3단계 배선으로 내려간다."*

## 산출물 ② — SW / HW 판정 기준표

강의의 판정표를 VIRA-1 증상으로 전면 재작성했습니다. **이 표가 6교시에서 가장 실용적인 산출물입니다.**

| 증상 | 판정 | 근거 (강의 대응 원문) | VIRA-1 1차 조치 |
|---|---|---|---|
| **특정 다이 좌표에서만 항상 미검** | **SW** | *"매번 똑같이 실패한다 → 결정적으로 동작하고 있다"* | ROI 크롭 오프셋, 웨이퍼 맵 좌표 매핑 확인 |
| **카메라 링크가 가끔 끊기고, 케이블을 만지면 복구** | **HW** | *"가끔 실패하고, 만지면 된다 → 접촉 불량"* | GigE 커넥터 락, 케이블 굽힘 반경, PoE 급전 확인 |
| **스트로브 발광 시 프레임 드롭 / 컨트롤러 리셋** | **HW · 전원** | *"모터를 켜면 보드가 꺼진다 → 전류 용량 부족"* | **24V-ILL 강하 실측.** 커패시터 뱅크 위치·용량 재검토 |
| **마스크는 정상인데 µm 환산값이 스펙과 안 맞음** | **SW** | *"값은 오는데 숫자가 이상하다 → 단위·스케일·미보정"* | 픽셀-실치수 변환 계수 재캘리브레이션 |
| **가동 4시간 후 미검율 상승** | **HW** | *"시간이 지날수록 나빠진다 → 발열·전압 하강"* | 스트로브 광량 모니터(AI-01) 추이 확인, GPU 스로틀링 로그 |
| **오프라인 검증은 통과인데 인라인에서 검출률 하락** | **HW · 입력** | *"모델이 아니라 입력이 달라진 것이다"* | **진동 블러 · 조명 광량 · 모달리티(Mono/컬러) 3종 우선 확인** |
| **I2C 센서 5개 중 일부만 읽힘** | **HW · 설정** | *"주소 충돌이다. I2C 스캔을 돌리면 즉시 보인다"* | I2C 스캔 → AD0/SDO 핀 설정 확인 |
| **판정은 나오는데 엉뚱한 다이가 배출됨** | **SW · 동기** | — (VIRA-1 고유) | 판정 패킷의 좌표·시퀀스 번호 대조 (§2 요구사항 B) |

> **마지막 행은 강의에 없는 VIRA-1 고유 실패 모드**입니다. 이동 로봇은 자기 자신이 하나지만, VIRA-1은 **판정 대상이 초당 4개씩 흘러가는 파이프라인**이라 "어느 다이의 판정인가"를 잃어버리는 실패가 존재합니다. 가장 위험한 실패 모드이므로 설계 단계에서 좌표·시퀀스 대조를 강제했습니다.

강의 Interactive 16의 명제: **"하드웨어 지식이 곧 프롬프트 품질이다."**
`PBX` 배열이 정의한 6개 요소를 VIRA-1에 채웠습니다. 각 요소의 `why`는 강의 원문입니다.

| # | 요소 | 강의가 말하는 이유 |
|---|---|---|
| 1 | 하드웨어 명시 | *"보드와 프레임워크를 안 쓰면 AI가 Arduino Uno용 코드를 줄 수도 있다"* |
| 2 | 핀 배선 명시 | *"핀 번호가 없으면 AI는 임의의 핀을 고른다. 그 핀이 스트래핑 핀이면 보드가 안 켜진다"* |

### VIRA-1 검사 파이프라인 프롬프트 (6요소 전부 반영)

```
[1 하드웨어]
산업용 IPC (Ubuntu 22.04, NVIDIA RTX A4000, TensorRT 10, CUDA 12) 위에서
동작하는 Python 검사 서비스를 작성한다. 모션 컨트롤러와는 EtherCAT로 연결된다.

[2 채널 · 인터페이스 배선]
카메라: GigE Vision 3채널, 각각 독립 NIC (enp1s0=동축, enp2s0=다크필드L,
        enp3s0=다크필드R). 프레임 2448x2048 mono8, 채널당 259 Mbps.
환경센서: I2C — 진동 0x68(카메라마운트)/0x69(스테이지), 온습도 0x76/0x77, 조도 0x23.
스트로브 광량 모니터: AI-01 (0~10V).
※ 카메라 3대를 하나의 NIC에 바인딩하지 말 것. 776 Mbps로 1GbE 실효 대역을 초과한다.

[3 동작 주기 · 조건]
스테이지 Step & Settle 방식. 스텝당 이송 12.0mm(200mm/s) → 정정 80ms → 3채널 촬상.
촬상은 정지 상태에서만 수행한다(이동 중 촬상 시 200us 발광으로 8px 블러 발생).
프레임당 다이 3x3=9개를 배치 추론한다.
스캔·추론·픽업은 반드시 별도 큐로 분리한다. 9다이 직렬 추론은 1,080ms로
스텝 시간 155ms를 초과하므로 같은 스레드에 묶으면 즉시 병목이 된다.

[4 데이터 형식]
판정 결과는 다음 스키마로 발행한다.
{ "wafer_id", "lot_id", "row", "col", "seq", "ts",
  "verdict": "PASS|REVIEW|REJECT",
  "defects": [{"cls","mask_area_um2","length_um","conf"}],
  "model_ver", "latency_ms" }
MQTT 토픽: fab/{line}/{tool}/verdict
웨이퍼 맵은 SEMI E142 포맷으로 출력한다.

[5 예외 처리]
- 프레임 드롭 발생 시 해당 다이를 PASS로 처리하지 말고 REVIEW로 강제 분류한다.
- 진동 센서 값이 임계(2um) 초과면 해당 프레임을 재촬상하고, 3회 연속 실패 시 인터록.
- 스트로브 광량이 기준의 85% 미만이면 경고를 발행하되 검사는 계속한다.
- EtherCAT heartbeat가 500ms 이상 끊기면 모션 컨트롤러가 HOLD로 전이한다.
- IPC 재시작 시 유효 heartbeat 수신 전까지 픽업을 시작하지 않는다(기본 상태 HOLD).
- 판정 패킷의 (row, col, seq)가 현재 픽업 대상과 불일치하면 즉시 인터록.

[6 검증 방법]
기동 시 다음을 로그로 출력한다.
- I2C 스캔 결과 (0x68/0x69/0x76/0x77/0x23 전부 검출되는지)
- 카메라 3대 열거 결과와 각 NIC 바인딩 상태
- GPU 인식 및 TensorRT 엔진 로드 성공 여부
- 각 레일 전압 실측값
런타임에는 채널별 프레임 드롭 수, 다이당 추론 지연 P50/P95/P99,
스트로브 광량 추이를 Prometheus 메트릭으로 노출한다.
```

> **강의가 남기는 한 문장** — *"하드웨어를 아는 만큼 프롬프트가 정확해지고, 프롬프트가 정확한 만큼 제품이 동작한다."*
> 위 프롬프트에서 `776 Mbps로 1GbE 실효 대역을 초과한다`, `200us 발광으로 8px 블러`, `9다이 직렬 추론은 1,080ms` 같은 문장은 **1~5교시의 계산을 마친 사람만 쓸 수 있는 문장**입니다. 이것이 강의가 말하는 프롬프트 품질의 실체입니다.

## 맺음 — 이 강의를 VIRA-1에 대입해서 얻은 것

강의는 이동 로봇을 전제로 설계되어 있고 VIRA-1은 고정형 검사 설비이므로, 배터리 용량 산정과 주행 토크 계산 두 항목은 직접 적용되지 않았습니다. 그 외 **모든 항목이 그대로 성립**했고, 특히 세 지점에서 강의의 프레임이 실제 설계 오류를 잡아냈습니다.

1. **"평균이 아니라 피크로 설계한다"** → 스트로브 조명이 시스템의 숨은 최대 부하임을 드러냄 (피크/평균 9.3배)
2. **"핀은 빈 자리가 아니라 정해진 자리다"** → GigE 대역폭 충돌 발견 (단일 포트 여유 21%)
3. **"모터 진동 → 카메라 흔들림 → AI 인식률 하락. 기구가 곧 성능이다"** → 이동 촬상 시 8 px 블러 정량화, Step & Settle 확정

세 가지 모두 **AI 모델을 아무리 잘 학습시켜도 해결되지 않는 문제**입니다. 학습 리포트가 *"광학이 확보되지 않으면 모델로 보완 불가"* 라고 쓴 것과 같은 이야기이며, 강의의 마지막 문장이 그것을 요약합니다.

> **"AI가 짜준 코드를 고치기 전에, 전원과 GND부터 확인한다."**
