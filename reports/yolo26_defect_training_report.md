## 2. 태스크 — `yolo26s-seg` (v2와 동일)

AABB 채움비 6.8%. 축정렬 박스는 93%가 빈 공간이므로 detect는 부적합합니다.

- 박스 회귀 손실의 93%가 정상 패턴을 맞추는 데 소모됨
- 모델이 "큰 박스"를 학습 → 사실상 분류기가 됨
- 스크래치 길이·면적 측정 불가 → 합부 판정에 못 씀

폴리곤 라벨을 이미 보유했으므로 추가 비용 없이 `-seg`로 갈 수 있습니다.

### `mask_ratio` — Colab에서 개선 가능해진 항목

기본 `mask_ratio=4`는 마스크를 4배 다운샘플합니다. 5px 미세 크랙이 마스크 공간에서 1.25px가 되어 소실됩니다.

v2에서는 8GB 제약 때문에 `2`로 타협했는데, **Colab에서는 `1`이 가능합니다.**

| GPU | 권장 `mask_ratio` | 근거 |
|---|---|---|
| T4 16GB (무료) | **2** | 1로 올리면 batch를 절반으로 줄여야 함 |
| L4 24GB (Pro) | **1** | 얇은 크랙 완전 보존 |
| A100 40GB (Pro+) | **1** | 여유 충분 |

`mask_ratio=1`은 마스크를 원본 해상도로 학습하므로 3~5px 크랙도 손실 없이 supervision을 받습니다. **이 데이터에서 가장 큰 성능 이득이 여기서 나올 가능성이 높습니다.**

## 3. Colab 리소스 설계 ★v3 핵심 변경

### GPU 등급별 배정 (추정 — `batch=-1`로 실측 권장)

`yolo26s-seg`, `imgsz=832`, AMP on 기준:

| GPU | VRAM | `batch` | `mask_ratio` | 특성 |
|---|---|---|---|---|
| **T4** (무료) | 16GB | 16 | 2 | Turing. FP16 텐서코어 O, BF16 X. 느림 |
| **L4** (Pro) | 24GB | 24 | 1 | Ada. T4의 약 2배 속도 |
| **A100** (Pro+) | 40GB | 40 | 1 | T4의 약 4배 속도 |

**세션마다 배정되는 GPU가 다릅니다.** batch를 코드에 하드코딩하면 어느 날 OOM, 어느 날 VRAM 절반 낭비가 됩니다. 노트북에서 `torch.cuda.get_device_properties(0).total_memory`로 자동 분기하도록 작성했습니다.

### VRAM 여유를 어디에 쓸 것인가 — imgsz가 아닙니다

**중요: `imgsz`를 832 이상으로 올리지 마세요.** 원본이 811px이므로 그 위는 순수 업스케일이고 정보 이득이 0인데 연산만 늘어납니다. 해상도 상한은 VRAM이 아니라 **데이터가 정합니다.**

VRAM 여유는 이 순서로 쓰세요.

1. **`mask_ratio` 4 → 2 → 1** (얇은 결함 supervision 개선. 가장 큰 이득)
2. **`batch` 증가** (T4 16 / L4 24 / A100 40. 학습 안정성)
3. 그다음에도 남으면 `yolo26m-seg` 시도 (단 1,000장이면 과적합 위험)

### 시간 예산 — Colab의 진짜 제약

| 세션 종류 | 최대 실행 | 유휴 종료 | 비고 |
|---|---|---|---|
| 무료 | 약 12시간 | 약 90분 | GPU 미배정될 수 있음. 사용량 제한 有 |
| Pro | 약 24시간 | 더 길음 | 컴퓨팅 단위 소모 |
| Pro+ | 약 24시간 | 백그라운드 실행 | |

*(정책은 변경될 수 있으니 현재 값은 Colab 문서에서 확인하세요)*

### 에폭당 소요 추정

`yolo26s-seg`, 832px, `cache` 사용, val 포함:

| 데이터 | T4 | L4 | A100 |
|---|---|---|---|
| 700장 (타일링 없음) | ~55초 | ~28초 | ~15초 |
| 3,000 타일 | ~235초 | ~120초 | ~62초 |

**200에폭 총 소요 (추정)**

| 데이터 | T4 | L4 | A100 |
|---|---|---|---|
| 700장 | 3.1시간 ✅ | 1.6시간 ✅ | 0.8시간 ✅ |
| 3,000 타일 | **13시간 ❌** | 6.7시간 ✅ | 3.4시간 ✅ |

> **결론: 무료 T4 + 타일링 조합은 단일 세션에 들어가지 않습니다.**
> 세 가지 중 하나를 택하세요.
> 1. **타일링하지 않는다** — 업로드본이 실제 샘플 크기(811px)라면 원래 필요 없습니다
> 2. **에폭을 120으로 줄이고 `patience=20`** — 조기 종료가 먼저 걸릴 가능성이 높습니다
> 3. **Pro로 L4를 쓴다** — freeze/mask_ratio 스윕까지 하려면 이게 현실적입니다

### 데이터 스테이징 — Drive를 직접 읽으면 안 됩니다

이게 Colab에서 가장 자주 놓치는 성능 문제입니다.

Google Drive 마운트는 **파일당 지연이 큽니다.** 작은 파일 수천 개를 매 에폭 읽으면 GPU가 계속 대기합니다. 강의 2장의 I/O 병목 챕터가 여기서 로컬 디스크보다 훨씬 심하게 나타납니다.

| 방식 | 1,000장(약 2GB) 전송 | 학습 중 |
|---|---|---|
| Drive 직접 읽기 | — | **매 에폭 병목** |
| Drive에서 파일 1,000개 개별 복사 | 5~15분 | 빠름 |
| **Drive에 zip 1개 → 복사 → /content에서 해제** | **1~3분** | 빠름 |

**권장 절차**

```
1) 로컬에서 dataset.zip 하나로 압축 → Drive에 업로드 (1회)
2) 세션 시작 시: Drive의 zip을 /content로 복사 (1개 큰 파일이라 빠름)
3) /content에서 해제 → /content/dataset (Colab 로컬 SSD, 빠름)
4) cache=True 또는 cache='disk'
5) 체크포인트만 Drive에 저장
```

### RAM과 `cache` 선택

무료 티어 RAM은 약 12.7GB입니다. `cache=True`는 리사이즈된 이미지를 RAM에 올립니다.

```
필요 RAM ≈ 이미지 수 × 832 × 832 × 3 bytes
```

| 데이터 | 필요 RAM | 무료 티어 판정 |
|---|---|---|
| 1,000장 | 2.1 GB | ✅ `cache=True` |
| 3,000 타일 | 6.2 GB | ⚠️ 위험 (Colab 자체 점유 감안) |
| 5,000 타일 | 10.4 GB | ❌ `cache='disk'` |

`cache='disk'`는 `.npy`를 디스크에 씁니다. **/content는 빠른 SSD이므로 이 옵션이 잘 작동합니다.** 단 데이터가 /content에 있을 때만 그렇습니다(Drive면 의미 없음).

강의가 지적한 함정 그대로 — **캐싱은 1에폭에 효과가 없고 오히려 느립니다.** 3에폭 벤치마크로 판단하지 마세요.

### `workers` — vCPU 수에 맞춰야 합니다

무료 티어는 vCPU가 2개입니다. 기본값 8은 컨텍스트 스위칭 오버헤드만 만듭니다.

```python
import os
workers = min(8, os.cpu_count())   # 무료 T4면 2, Pro L4면 8~12
```

세그멘테이션은 마스크 처리 때문에 detect보다 데이터로더 부담이 큽니다. `cache`를 쓰면 이 부담이 대폭 줄어드니 반드시 켜세요.

### 세션 끊김 대비 — 체크포인트 설계

**/content는 세션 종료 시 전부 삭제됩니다.** 학습 결과를 잃지 않으려면 `project`를 Drive에 두어야 합니다.

```python
project='/content/drive/MyDrive/yolo_runs'
save_period=10        # 10에폭마다 별도 스냅샷 (last.pt/best.pt와 별개)
```

Ultralytics는 매 에폭 `last.pt`를 씁니다. `yolo26s-seg`가 약 25MB이므로 Drive 쓰기에 5~10초가 추가됩니다. T4에서 에폭이 55초면 약 10~15% 오버헤드입니다.

**대안 (속도 우선)**: `project`를 `/content/runs`에 두고 20~30에폭마다 Drive로 rsync. 오버헤드가 거의 없지만, 마지막 동기화 이후 진행분은 세션이 끊기면 잃습니다.

**권장: Drive 직접 저장.** 10~15% 오버헤드는 학습을 처음부터 다시 돌리는 것보다 훨씬 저렴합니다.

**재시작**
```python
YOLO('/content/drive/MyDrive/yolo_runs/s_seg/weights/last.pt').train(resume=True)
```
`resume=True`는 `args.yaml`에서 원래 설정을 그대로 읽어옵니다. 다른 인자를 함께 주면 무시되거나 충돌하므로 **resume 시에는 다른 인자를 주지 마세요.**

### 유휴 종료 방지

약 90분간 상호작용이 없으면 세션이 종료됩니다. 학습 로그가 계속 출력되면 대개 유지되지만, 안전하게는 브라우저 탭을 열어두고 주기적으로 확인하세요. Pro+는 백그라운드 실행이 지원됩니다.

## 4. 증강 — 방향 히스토그램이 정하는 설정 (v2와 동일)

측정값 2(축정렬 엣지 63.7%)가 증강 정책을 결정합니다.

### `mosaic=0.0` — 켜면 가짜 크랙을 주입합니다

모자이크는 4장을 이어붙이고 경계에 하드 이음선을 만듭니다. 주기적 회로 패턴에서 이음선은 **"패턴이 갑자기 끊긴 직선"** — 크랙의 시각적 정의 그 자체입니다. 라벨 없는 크랙 유사 구조를 대량 주입하므로 실제 크랙 검출력이 깎입니다.

```python
mosaic=0.0
close_mosaic=0
```

### `degrees=0.0` — 임의 각도 회전 절대 금지

"대각선 = 결함, 축정렬 = 패턴"이 이 데이터에서 가장 강력한 판별 규칙입니다. 임의 각도 회전은 정상 패턴을 대각선으로, 결함을 축정렬로 만들어 이 규칙을 무효화합니다.

90° 배수 회전은 맨해튼 기하를 보존하므로 안전합니다. 데이터 증폭이 필요하면 오프라인으로 90/180/270° 회전본을 만들어 데이터셋에 추가하세요(Colab 세션 시작 시 1회 생성).

### `copy_paste=0.3` — 희소 클래스의 정답

폴리곤 라벨이 있으므로 실제 결함을 실제 정상 이미지에 이식할 수 있습니다. 물리적으로 타당한 유일한 증강이며, 크랙 같은 희소 클래스에 대한 직접적 해법입니다.

수동으로 하면 더 세밀하게 통제됩니다.
- 결함을 **같은 영역 타입**(어레이는 어레이에, 배선부는 배선부에)에 붙일 것
- 가법 합성으로 국소 대비만 이식, 배경 밝기는 유지
- 각도는 무작위로 주되 **축정렬(0°/90° ±10°)은 피할 것**

### 증강 설정 확정표

| 인자 | 기본값 | 권장값 | 근거 |
|---|---|---|---|
| `mosaic` | 1.0 | **0.0** | 이음선 = 가짜 크랙 주입 |
| `close_mosaic` | 10 | 0 | mosaic 미사용 |
| `degrees` | 0.0 | **0.0** | 축정렬 63.7% 단서 보존 |
| `scale` | 0.5 | 0.2 | 결함 크기가 합부 판정 기준 |
| `translate` | 0.1 | 0.1 유지 | — |
| `fliplr` | 0.5 | 0.5 유지 | 축정렬 보존, 방향 다양성 |
| `flipud` | 0.0 | **0.5** | 동일 (방향성 조명이면 0) |
| `copy_paste` | 0.0 | **0.3** | 희소 클래스 대응 |
| `hsv_h` | 0.015 | **0.0** | 색상이 결함 신호 |
| `hsv_s` | 0.7 | 0.0 | 동일 |
| `hsv_v` | 0.4 | 0.3 | 조명 드리프트만 |
| `mixup` | 0.0 | 0.0 유지 | 두 다이 혼합은 물리적 무의미 |
| `multi_scale` | False | False | 카메라 고정 |

**방향성 조명(측광·저각도 암시야)을 쓴다면 플립을 0으로.** 결함의 산란 방향이 조명 방향으로 결정되므로 플립은 물리적으로 불가능한 명암 배치를 학습시킵니다.

## 5. 클래스 설계 (v2와 동일)

### 5종을 그대로 쓰지 마세요

이미지 2를 저도 스크래치인지 크랙인지 단정할 수 없습니다. 선형 결함 안에 재료 결손 흔적이 있어 "치핑 동반 스크래치"일 수도, "부스러진 크랙"일 수도 있습니다. 검사원 사이에서도 갈리는 유형이며, 즉 **두 클래스 사이에 라벨 노이즈가 구조적으로 존재합니다.**

### 형태 기반 3클래스

| 클래스 | 포함 | 형태 특성 |
|---|---|---|
| `linear` | 스크래치, 크랙 | 종횡비 5:1 이상, 대각 우세 |
| `blob` | 파티클, 치핑 | 종횡비 3:1 이하, 조밀 |
| `area` | 변색, 산화, 얼룩 | 저대비 넓은 영역 |

스크래치와 크랙은 형태가 같아서 모델 입장에서 같은 클래스가 자연스럽습니다. 유형 세분은 검출된 마스크를 크롭해 별도 분류기로 처리하세요 — 분류는 검출보다 데이터 요구량이 훨씬 낮고, **Colab에서 분류기 학습은 몇 분이면 끝납니다.**

판별 단서 참고:
- 스크래치: 폭이 일정, 잔해가 진행 방향으로 밀려 있음
- 크랙: 폭이 불규칙, 분기(branching), 끝이 뾰족하게 수렴

## 6. freeze와 옵티마이저

### 중간 도메인 — 3종 비교 필수

- **저수준 특징(엣지·코너·텍스처·주기성)은 전이됩니다.** 광학 현미경 영상이고 SAR·초음파처럼 픽셀 통계가 근본적으로 다른 부류가 아닙니다
- **고수준 특징(물체 의미)은 무용합니다.** COCO의 "개·차·사람"에 대응물이 없습니다

`freeze=10`이 1순위 후보(YOLO26 백본 0~10 중 마지막 C2PSA만 학습)지만, `None`이 이길 여지가 실제로 있습니다.

**Colab에서는 스윕 비용이 시간이므로 에폭을 캡하세요.** 순위만 보면 되니 60~80에폭으로 충분합니다. 강의 3장의 `fraction` 철학과 같은 논리입니다.

| freeze | 스윕 에폭 | 가설 |
|---|---|---|
| `10` | 80 | 백본 저수준 유지 + 고수준 적응 |
| `None` | 80 | 텍스처 통계 차이로 전체 재학습이 유리 |
| `23` | 80 | 헤드만 — 희소 클래스 대응 |

T4에서 3종 × 80에폭 × 55초 = **약 3.7시간**. 단일 세션에 들어갑니다.

### 옵티마이저 — `auto` 금지 (v2와 동일하나 수치가 바뀝니다)

`optimizer='auto'`는 총 반복 횟수로 옵티마이저와 학습률을 정하고 `lr0`을 덮어씁니다.

```
iterations = epochs × (train장수 / batch)
분기 ≈ 10,000  (초과 시 SGD lr0=0.01, 이하 시 AdamW lr0≈0.00167)
```

**Colab batch로 재계산 (train 700장 기준)**

| GPU | batch | SGD 전환 epoch |
|---|---|---|
| T4 | 16 | 229 |
| L4 | 24 | 343 |
| A100 | 40 | 571 |

배치가 커지면서 분기점이 멀어져 대부분 AdamW가 선택됩니다. 하지만 **GPU가 세션마다 바뀌면 batch가 바뀌고, 그럼 옵티마이저와 학습률이 조용히 달라집니다.** 어제 실험과 오늘 실험이 비교 불가능해집니다.

Colab에서는 이 함정이 로컬보다 더 위험합니다. **반드시 명시하세요.**

```python
optimizer='AdamW', lr0=0.001, lrf=0.01, warmup_epochs=3.0, cos_lr=True
```

`freeze=None`으로 전체 학습할 때는 `SGD, lr0=0.01`이 대안입니다.

### epochs와 patience

```python
epochs=200, patience=25
```

강의 권장 10~20을 25로 올린 이유는 val이 150장 수준이면 에폭별 mAP가 크게 출렁이기 때문입니다. patience=10이면 일시적 하락에서 조기 종료가 걸려 진짜 최고점을 놓칩니다.

**타일링해서 무료 T4를 쓴다면** `epochs=120, patience=20`으로 줄이세요. 조기 종료가 먼저 걸릴 가능성이 높으니 실질 손실은 작습니다.

## 8. 평가 — mAP가 아니라 미검율 (v2와 동일)

세장형 마스크에서 mAP50-95는 폭 1~2px 차이로 크게 흔들리는데 그 차이는 합부 판정에 영향이 없습니다.

**주 지표: 마스크 mAP50.** 실제 의사결정은 아래로 합니다.

| 지표 | 정의 | 목표 |
|---|---|---|
| **이미지 단위 미검율** | 결함 이미지 중 마스크 0개인 비율 | 최우선 최소화 |
| **이미지당 오검 개수** | 정상 이미지에서 나온 마스크 수 | 과검 예산 내 |
| 마스크 면적 오차 | 예측 면적 / 정답 면적 | 합부 판정 정확도 |

```python
m.val(data="...", conf=0.001, iou=0.7, plots=True)
# MaskPR_curve.png 에서 Recall 우선 지점 선택
```

미검 최소화가 목표면 **Recall 0.99를 만족하는 최저 conf**를 배포값으로 쓰고, 애매한 구간은 사람 재검으로 넘기는 3-way 판정을 두세요.

```
conf < T_low        → 통과
T_low ~ T_high      → 사람 재검 (VRS)
conf ≥ T_high       → 불량 확정
```

미검 0%는 통계적으로 검증 불가능합니다. 검증셋 결함이 수백 개면 미검 0건이어도 95% 신뢰 상한은 수 % 수준입니다.

### 데이터 분할

배경이 모든 다이에서 거의 동일하므로 랜덤 분할은 성능을 크게 부풀립니다.

- **다이/웨이퍼 단위 그룹 분할** — 같은 다이의 다른 크롭이 train/val에 흩어지면 안 됨
- 타일링했다면 **원본 이미지 단위**로 분할
- 로트 정보가 있으면 로트 단위가 더 안전
- train 70% / val 15% / test 15%, test는 최종 1회만

## 부록 B — YOLO 단독보다 나을 수 있는 접근

이 데이터의 본질은 **"동일한 패턴이 반복되는 표면에서 예외를 찾는 것"**입니다. 모든 다이가 같은 레티클로 만들어져 픽셀 단위로 거의 동일합니다.

이 경우 **인접 다이와의 차분(die-to-die comparison)**이 강력합니다. 회로 패턴의 정상 반사는 인접 다이에서 똑같이 재현되는 공통 성분이라 차분에서 소거되고 결함만 남습니다. 반도체 검사 장비가 실제로 쓰는 방식입니다.

실무적으로는 **차분으로 후보를 뽑고(고감도) → YOLO-seg로 판정(과검 억제)** 하는 2단 구조가 YOLO 단독보다 유리할 가능성이 높습니다. 다이 서브픽셀 정렬이 전제라 구현 부담이 있으니, YOLO 단독 성능을 먼저 측정하고 미검율이 목표에 못 미칠 때 검토하세요.
