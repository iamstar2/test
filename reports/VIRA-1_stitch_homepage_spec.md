## 2. 문제 정의 섹션

### 2-1. 카피 (3카드 레이아웃)

| 카드 | 제목 | 본문 |
|---|---|---|
| 1 | **결함은 규칙으로 기술되지 않는다** | 스크래치의 픽셀 패턴은 길이·폭·깊이·조명 각도에 따라 연속적으로 변합니다. "밝기 차 20 이상, 길이 3px 이상" 같은 임계값으로는 허용 가능한 표면 텍스처와 불량을 분리할 수 없습니다. |
| 2 | **사람의 판정은 재현되지 않는다** | 검사원 간 판정 일치율 약 82%(가정). 야간 조 후반 3시간의 검출률은 주간 대비 11%p 낮습니다. 같은 제품이 조에 따라 양품·불량으로 갈립니다. |
| 3 | **박스로는 측정할 수 없다** | 축정렬 박스(AABB) 안에서 실제 결함이 차지하는 면적은 **6.8%**. 나머지 93%는 정상 패턴입니다. 박스 출력으로는 스크래치의 길이·면적을 산출할 수 없어 합부 판정에 쓸 수 없습니다. |

### 2-2. 기존 방식의 한계 (표)

| 기존 방식 | 한계 |
|---|---|
| 육안 전수 검사 | 피로에 따른 검출률 저하, 판정 기준 불일치, 검사 이력 데이터 미확보 |
| 룰 기반 AOI | 조명 변화·표면 편차에 취약. 곡면 반사체 미세 스크래치 검출률 60~70% 수준. 신규 결함 추가 시 룰 재설계에 2~4주 |
| 샘플링(AQL) | 전수 보증 불가, 로트 단위 유출 리스크 잔존 |
| 후공정/출하 검사 | 발견이 늦어 이미 투입된 가공비·부품비가 전량 손실 |

> ⚠️ **PRD 대비 조정** — PRD §1.1의 DPPM·클레임 건수·과검 손실 수치는 **가정값**입니다. 홈페이지에는 "업계 일반" 또는 "가정 기준" 라벨을 반드시 병기하세요.

## 3. 솔루션 섹션 — 3단 하이브리드 파이프라인

### 3-1. 파이프라인 다이어그램 (가로 5단 플로우로 시각화)

```
촬상  →  전처리  →  ┌ 3-1 부품/구조 검사 ┐  →  후처리  →  판정 3분기
(HW트리거)  (ROI·정합)  │ 3-2 표면 결함 seg │   (면적·길이)   (OK/REVIEW/NG)
                        └ 3-3 미학습 이상탐지┘                    ↓
                                                              PLC 자동 배출
```

| 단계 | 처리 내용 | 사용 기법 | 목표 지연 |
|---|---|---|---|
| 전처리 | ROI 크롭, 왜곡 보정, 정합, 명암 정규화 | OpenCV (룰 기반) | 15ms |
| 3-1 구조 검사 | 정합 ROI별 존재/종류 판별 | 템플릿 매칭 + ResNet-18 | 20ms |
| **3-2 표면 결함 검출** | **결함의 위치와 픽셀 영역 동시 출력** | **YOLO26s-seg** | **45ms** |
| 3-3 미학습 이상 탐지 | 정상 분포 대비 이질 영역 스코어링 | PatchCore (양품 only) | 30ms |
| 후처리 | 면적·길이 산출, 규격 대조, 임계값 적용 | 룰 기반 | 10ms |

### 3-2. 판정 3분기 (색상 강조 카드 3개)

| 판정 | 조건 | 후속 처리 | 색상 |
|---|---|---|---|
| **OK** | 최대 결함 스코어 < 0.35 | 라인 통과 | `#10B981` |
| **REVIEW** | 스코어 0.35~0.70, 또는 이상 탐지 단독 발생 | 재판정 트레이 분리, 운영자 확인 | `#F59E0B` |
| **NG** | Critical 결함 검출 또는 스코어 ≥ 0.70 | 자동 배출 | `#EF4444` |

> **핵심 메시지** — 미검 최소화가 목표라면 mAP가 아니라 **Recall 0.99를 만족하는 최저 conf**를 배포값으로 씁니다. 애매한 구간은 사람에게 넘기는 3-way 판정이 과검과 미검의 트레이드오프를 운영 파라미터로 만듭니다.

## 4. ★ 왜 YOLO26s-seg인가 — 근거 섹션 (홈페이지 핵심)

> 이 섹션은 **홈페이지에서 가장 비중 있게 다뤄야 하는 부분**입니다. 3단 논증 구조(태스크 → 아키텍처 → 모델 크기)로 시각화하세요.

### 4-1. 1단계 — 왜 detect가 아니라 seg인가 (실측 근거)

업로드된 결함 이미지 1장에서 동일 결함을 세 가지 방식으로 표현했을 때의 **실측값**입니다.

| 표현 방식 | 크기 | 면적 | **결함 채움비** | 판정 |
|---|---|---|---|---|
| 축정렬 박스 (Detect / AABB) | 423 × 623 | 263,529 px² (이미지의 52.1%) | **6.8%** | ❌ |
| 회전 박스 (OBB) | 752 × 60, 121.7° | 45,288 px² | 39.6% | △ |
| **폴리곤 (Seg)** | — | 약 17,918 px² | **100%** | ✅ |

**detect를 배제하는 이유 3가지**
1. 박스 회귀 손실의 **93%가 정상 패턴을 맞추는 데 소모**됩니다.
2. 모델이 "큰 박스 하나"를 학습해 사실상 분류기로 퇴화합니다.
3. **스크래치 길이·면적을 측정할 수 없어 합부 판정에 못 씁니다.** (PRD §3의 "길이 ≥1.5mm는 Critical" 규격을 적용할 방법이 없음)

> OBB는 채움비 39.6%로 detect보다 낫지만, **면적 측정 정확도가 여전히 2.5배 과대**입니다. 폴리곤 라벨을 이미 보유하고 있으므로 seg 전환에 추가 라벨링 비용이 발생하지 않습니다.

**시각화 제안** — 동일 결함 위에 빨간 AABB / 주황 OBB / 시안 폴리곤을 겹쳐 보여주고, 채움비 6.8% → 39.6% → 100% 를 애니메이션 카운터로.

### 4-2. 2단계 — 왜 YOLO26인가 (YOLO 계열 비교)

| 후보 | 이 과제에 대한 평가 | 채택 |
|---|---|---|
| **YOLOv8-seg** | 세그멘테이션 성숙도·자료량은 최고. 다만 NMS 후처리가 필수라 배치 내 검출 수에 따라 **지연 시간이 변동**. PLC 배출 타이밍이 결정론적이어야 하는 인라인 검사에서는 P99 지연 관리가 불리 | ❌ |
| **YOLO11-seg** *(PRD 원안)* | v8 대비 파라미터 효율 개선. 실적 있는 안전한 선택이며 **폴백 후보 1순위**. 그러나 NMS 의존과 미세 객체 특화 손실 부재는 v8과 동일 | △ 폴백 |
| **YOLOv12-seg** | 어텐션 중심 구조로 정확도 이점이 보고되었으나, Jetson/TensorRT INT8 변환 경로의 현장 실적이 상대적으로 얕아 **배포 리스크**가 큼 | ❌ |
| **YOLO26s-seg** | ① **NMS-free 종단간(end-to-end) 추론** → 후처리 지연이 검출 수에 무관하게 일정, P99 지연 예측 가능 ② **DFL 제거** → export/INT8 양자화 경로 단순화, Jetson 배포 난이도 하락 ③ **미세·소형 객체 대응 손실 설계** → 3~5px 폭 크랙이 정확히 이 과제의 병목 | ✅ **채택** |
| Mask R-CNN / RT-DETR (비교군) | 마스크 품질은 우수하나 파라미터·지연이 커서 45ms 예산에 부적합. 라인 택트 2.0초를 맞추려면 실시간 단일 스테이지가 필수 | ❌ |

**이 과제에서 YOLO26을 선택하는 결정타는 지연 예측 가능성입니다.**
PRD가 요구하는 것은 평균 지연이 아니라 **P99 ≤ 200ms**입니다. NMS 기반 모델은 한 이미지에서 검출 후보가 폭증할 때(= 과검이 터질 때, 즉 가장 위험한 순간에) 후처리 시간이 함께 늘어납니다. NMS-free 구조는 이 최악 케이스를 구조적으로 제거합니다. PLC가 엔코더 기반으로 배출 시점을 계산하는 시스템에서 지연 지터는 곧 **오배출**입니다.

> ⚠️ **검증 필요** — YOLO26의 세부 아키텍처 주장(NMS-free / DFL 제거 / 소형 객체 손실)은 최신 릴리스 노트와 다를 수 있습니다. 홈페이지 게시 전 Ultralytics 공식 문서에서 재확인하시고, 필요하면 §9-1의 벤치마크 계획으로 자체 실측치를 확보한 뒤 문구를 확정하세요. **YOLO11-seg를 폴백으로 명시해 둔 이유가 이것입니다.**

### 4-3. 3단계 — 왜 `s` 크기인가 (2,000~4,000장 기준)

| 크기 | 판정 근거 | 결론 |
|---|---|---|
| `yolo26n-seg` | 파이프라인 검증·베이스라인용으로는 필수. 다만 3~5px 크랙의 표현력이 부족할 가능성 | 베이스라인 전용 |
| **`yolo26s-seg`** | 2,000~4,000장 규모에서 **용량과 과적합의 균형점**. Jetson Orin에서 45ms 예산 내 여유 확보 | ✅ **채택** |
| `yolo26m-seg` | 1,000장에서는 과적합 확정. **4,000장 상단 + `copy_paste` 증강 조합이라면 1회 시도 가치는 있음**. 단 지연 예산 재검증 필수 | 조건부 |

### 4-4. 결정타 — `mask_ratio` (여기서 가장 큰 성능 이득이 나옵니다)

기본값 `mask_ratio=4`는 마스크를 4배 다운샘플합니다. **5px 크랙이 마스크 공간에서 1.25px가 되어 소실됩니다.** 즉 모델이 얇은 결함에 대해 제대로 된 supervision을 받지 못합니다.

| GPU | VRAM | `batch` | `mask_ratio` | 효과 |
|---|---|---|---|---|
| T4 (Colab 무료) | 16GB | 16 | 2 | 타협값 |
| L4 (Pro) | 24GB | 24 | **1** | 얇은 크랙 완전 보존 |
| A100 (Pro+) | 40GB | 40 | **1** | 여유 충분 |

**VRAM 여유를 쓰는 우선순위** — `mask_ratio` 4→2→1 ▸ `batch` 증가 ▸ (그래도 남으면) `m-seg` 시도

> 🚫 **`imgsz`를 832 이상으로 올리지 마세요.** 원본이 811px이므로 그 위는 순수 업스케일이고 정보 이득이 0인데 연산만 늘어납니다. **해상도 상한은 VRAM이 아니라 데이터가 정합니다.**

## 5. 성능 지표 섹션

### 5-1. 목표 KPI (홈페이지 지표 카드)

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| Critical 결함 검출률 (Recall) | **≥ 99.5%** | 알려진 불량 샘플 200종 주간 시험 + 배출품 100% 재판정 |
| 미검출 유출률 | **≤ 50 DPPM** | 통과품 샘플링 재검 + 고객 입고 검사 결과 |
| 과검율 (False Positive) | **≤ 1.0%** | 배출품 재판정 결과 |
| REVIEW 발생률 | ≤ 2.0% | 시스템 로그 |
| 추론 지연 | P95 ≤ 120ms / P99 ≤ 200ms | Edge 단독 처리 |
| 판정 → 배출 완료 | ≤ 500ms | PLC 액추에이터 동작 포함 |
| 배출 정확도 | ≥ 99.9% | 인접 제품 오배출 0건 목표 |

### 5-2. "우리는 mAP로 홍보하지 않습니다" — 차별화 카피

> 세장형(細長型) 마스크에서 mAP50-95는 폭 1~2px 차이로 크게 흔들리지만, 그 차이는 합부 판정에 아무 영향이 없습니다. 그래서 VIRA-1은 학습 지표가 아니라 **현장 의사결정 지표**로 성능을 보고합니다.

| 우리가 보는 지표 | 정의 |
|---|---|
| **이미지 단위 미검율** | 결함 이미지 중 마스크가 하나도 나오지 않은 비율 — 최우선 최소화 |
| **이미지당 오검 개수** | 정상 이미지에서 나온 마스크 수 — 과검 예산 관리 |
| **마스크 면적 오차** | 예측 면적 ÷ 정답 면적 — 합부 판정 정확도 직결 |

> **정직성 문구 (신뢰 요소로 홈페이지에 명시 권장)**
> "미검 0%는 통계적으로 검증 불가능합니다. 검증셋 결함이 수백 개면 미검 0건이어도 95% 신뢰 상한은 수 % 수준입니다. VIRA-1은 0%를 약속하지 않고, **측정 가능한 상한과 사람 재검 경로**를 함께 제공합니다."

## 7. 학습 환경 섹션 (실측 반영 — PRD 대비 최대 변경 지점)

> 이 섹션은 홈페이지에서는 "기술 상세" 접이식 블록으로 처리하고, 전체 내용은 별도 기술 리포트 PDF로 제공하는 것을 권장합니다.

### 7-1. 데이터 규모 2,000~4,000장에 따른 재계산 ★

| 데이터 | 에폭 소요 (T4/L4/A100) | **200에폭 총 소요** | `cache=True` 필요 RAM |
|---|---|---|---|
| 2,000장 | 157s / 80s / 41s | 8.7h / 4.4h / **2.3h** | 4.2 GB ✅ |
| 3,000장 | 236s / 120s / 62s | **13.1h ❌** / 6.7h / 3.5h | 6.2 GB ⚠️ |
| 4,000장 | 314s / 160s / 83s | **17.4h ❌** / 8.9h / 4.6h | 8.3 GB ❌ |

**결론 3가지**
1. **Colab 무료 T4는 3,000장 이상에서 단일 세션(약 12h)에 들어가지 않습니다.** → Pro(L4) 이상 필수, 또는 `epochs=120, patience=20`으로 축소.
2. **3,000장 이상은 `cache='disk'`로 전환하세요.** 무료 티어 RAM 12.7GB에서 `cache=True`는 Colab 자체 점유를 감안하면 위험합니다. (`/content`는 빠른 SSD이므로 disk 캐시가 잘 작동합니다. **Drive에 두면 의미 없습니다.**)
3. **Drive를 직접 읽지 마세요.** zip 1개로 묶어 `/content`에 복사 후 해제 → 1~3분. 파일 1,000개 개별 복사는 5~15분, Drive 직접 읽기는 **매 에폭 병목**입니다.

### 7-2. `optimizer='auto'` 금지 — 데이터가 늘면서 함정이 커졌습니다 ★

`auto`는 총 반복 횟수 10,000을 기준으로 옵티마이저와 `lr0`을 **조용히 바꿉니다.** 데이터가 1,000 → 3,000장으로 늘면서 분기점이 앞당겨졌습니다.

| 데이터 | GPU / batch | SGD 전환 에폭 |
|---|---|---|
| 2,000장 | T4 / 16 | 114 |
| **3,000장** | **T4 / 16** | **76** |
| 3,000장 | L4 / 24 | 114 |
| **4,000장** | **T4 / 16** | **57** |
| 4,000장 | A100 / 40 | 143 |

**무슨 일이 벌어지나** — 80에폭 스윕은 AdamW로, 200에폭 최종 학습은 중간에 SGD로 넘어갑니다. **스윕 결과와 최종 결과가 비교 불가능해집니다.** 게다가 Colab은 세션마다 GPU가 바뀌므로 batch가 바뀌고, 그러면 분기점도 바뀝니다. 어제 실험과 오늘 실험이 다른 옵티마이저로 돌아간 걸 모른 채 결론을 냅니다.

```python
optimizer='AdamW', lr0=0.001, lrf=0.01, warmup_epochs=3.0, cos_lr=True   # 반드시 명시
```

### 7-3. 증강 — 방향 히스토그램이 정합니다

측정 결과 **회로 패턴 엣지의 63.7%가 축정렬(수평·수직 ±10°)** 인 반면, 스크래치는 **121.7° 대각**입니다.

> **"대각선 = 결함, 축정렬 = 패턴"이 이 데이터에서 가장 강력한 판별 규칙입니다.**

| 인자 | 기본값 | **권장값** | 근거 |
|---|---|---|---|
| `mosaic` | 1.0 | **0.0** | 모자이크 이음선 = 패턴이 갑자기 끊긴 직선 = **가짜 크랙 대량 주입** |
| `degrees` | 0.0 | **0.0** | 임의 각도 회전은 판별 규칙 자체를 무효화 (90° 배수는 오프라인으로만 허용) |
| `copy_paste` | 0.0 | **0.3** | 실제 결함을 실제 정상 이미지에 이식. **희소 클래스에 물리적으로 타당한 유일한 증강** |
| `hsv_h` / `hsv_s` | 0.015 / 0.7 | **0.0 / 0.0** | 색상 자체가 결함 신호 |
| `scale` | 0.5 | 0.2 | 결함 크기가 곧 합부 판정 기준 |
| `flipud` | 0.0 | 0.5 | 단 **방향성 조명(다크필드·측광)이면 0.0** — 산란 방향이 조명으로 결정되므로 |
| `mixup` | 0.0 | 0.0 | 두 다이 혼합은 물리적으로 무의미 |

### 7-4. 클래스 설계 — 5종을 그대로 쓰지 마세요

스크래치와 크랙은 **검사원 사이에서도 판정이 갈립니다.** 즉 두 클래스 사이에 라벨 노이즈가 구조적으로 존재합니다.

| 클래스 | 포함 | 형태 특성 |
|---|---|---|
| `linear` | 스크래치, 크랙 | 종횡비 5:1 이상, 대각 우세 |
| `blob` | 파티클, 치핑 | 종횡비 3:1 이하, 조밀 |
| `area` | 변색, 산화, 얼룩 | 저대비 넓은 영역 |

유형 세분화는 **검출된 마스크를 크롭해 별도 분류기로 2단 처리**합니다. 분류는 검출보다 데이터 요구량이 훨씬 낮습니다.

### 7-5. 데이터 분할 — 랜덤 분할 금지 ★

배경이 모든 다이에서 거의 동일하므로 **랜덤 분할은 성능을 크게 부풀립니다.**
→ **다이/웨이퍼 단위 그룹 분할** (같은 다이의 다른 크롭이 train/val에 흩어지면 안 됨). 로트 정보가 있으면 로트 단위가 더 안전. `train 70% / val 15% / test 15%`, **test는 최종 1회만.**
